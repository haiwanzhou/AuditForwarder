# 任务 4 执行方案：基于新采集器 + 新合谋检测模块，做真实管理系统合谋实验

> 对应会议纪要：第一大点（1.2 / 1.4 / 1.6）、第七大点（7.1）
> 依赖：任务 2（采集器规则）、任务 3（检测模块）；部分依赖任务 1（去重）、任务 5（看结果的页面）
> 目标：把"发消息约定代号 = 合谋"的演示，换成"真人在真系统上做真操作 → 日志采集 → 关联分析 → 出证据链"

---

## 零、为什么这件事最容易翻车

老师否掉旧演示的原话是："不能只有一个消息，你得有实际的操作……否则写个 if 就判了，太简单。"

所以本任务的**成败点不在写代码，而在"动作能不能真的做出来"**：

1. **图书管理系统里没有"卸载磁盘""打快照"这种按钮**。R-001 剧本（删备份→卸载卷→快照）照抄会直接命不中，然后就会不自觉地退回"发消息模拟"——正好踩红线。
   → 必须先做**动作字典**（阶段 1），把抽象动作翻译成系统里真实能点的操作。
2. **两名操作员必须操作"同一个对象"**，否则资产组/对象级关联不成立，R-007 这类规则天然不命中。
3. **三台机时钟不同步**（偏差 > 1 秒），微秒级时间窗失效，多步序列规则全线失灵。
4. **受管系统如果是 HTTPS**，内置 HTTP 代理只能看到 CONNECT 隧道，采不到 URI —— 实验环境必须用明文 HTTP 部署。

## 阶段 0：确定并部署受管系统

### 0.1 选型必须同时满足 5 条（少一条后面就演不下去）

| # | 条件 | 为什么 |
|---|------|--------|
| 1 | Web 访问，且能用 **HTTP 明文**部署（自定义端口，如 18080） | HTTP 代理采集器只能解明文 |
| 2 | 有**角色/权限分级**，至少能开 2 个不同权限的账号 | 合谋的前提是"不同操作员" |
| 3 | 有**备份 / 恢复 / 导出 / 删除**类功能 | 才有"销毁数据"类动作可演 |
| 4 | 同一个资源（同一本书 / 同一张表 / 同一个报表）能被两个账号分别操作 | 关联的 key 要重合 |
| 5 | 有操作历史或可查看的列表页 | 便于人工对照"系统里真有这事" |

### 0.2 部署

- 位置：与 AuditForwarder 服务端同一台，或第三台独立主机（推荐**独立主机**，避免与服务端自身日志混淆）
- 固定 IP + 端口，记下 `host:port`（例：`bookhost:18080`）
- 建 3 个账号 → 对应 3 个 `operator_id`：

| 账号 | 角色 | operator_id | 主机 |
|------|------|-------------|------|
| reader01 | 普通读者 | op_reader | 客户端 A |
| editor01 | 图书管理员 | op_editor | 客户端 B |
| admin01 | 系统管理员 | op_admin | 客户端 C（或服务端主机） |

**验收**：三个账号都能登录系统、能看到彼此权限差异（reader 进不去后台）。

## 阶段 1：做"实验动作字典"（本任务最核心的一步）

这张表填不出来，实验就不要开始。

### 1.1 表格模板（逐行填，一行 = 剧本里的一个动作）

| 剧本 | 设计动作（抽象） | 在图书系统/主机上的真实操作 | 采集通道 | 预期 op_type / 关键字段 | 期望命中规则 |
|------|------------------|------------------------------|----------|--------------------------|--------------|
| A | 删除备份（人 1） | 后台"系统备份"页 → 删除某个备份文件 | http | DELETE /admin/backup/xxx | R-001 步骤 1 |
| A | 卸载备份卷（人 2） | 主机上真实执行：把备份盘符 dismount（`mountvol X: /D`） | process / etw | 4688 命令行含 mountvol | R-001 步骤 2 |
| A | 打快照（人 2） | 主机上真实执行：删除卷影副本 `vssadmin delete shadows` | process / etw | 4688 命令行含 vssadmin | R-001 步骤 3 |
| B | 提权（人 1） | 系统里把某账号提到 admin 角色 | http | PUT /admin/users/xx/role | R-004 步骤 1 |
| B | 导出全库（人 1） | 后台"数据导出"点全量导出 | http | GET /admin/export?all=1 | R-004 步骤 2 |
| B | 清表（人 2） | 后台"数据维护"→ 清空借阅记录 | http | POST /admin/maintain/clear | R-004 步骤 3 |
| C | 导出报表 + 清除（同一人） | 导出报表 → 删除该报表 | http | /reports/* | R-006（operator 分组） |
| D | 甲提权 → 乙导出同一对象 | 甲改权限，乙导出同一本书/同一报表 | http | 同一 res_key | R-007（object 分组） |

### 1.2 三条硬规则

1. **每个动作必须是"人能点出来的"或"命令能敲出来的"**，不许有人在旁边"手工发一条 JSON"。
2. **至少一个动作要跨通道**（HTTP + 进程/ETW 各一个），否则体现不出"跨系统、跨采集器关联"的卖点。
3. **不可恢复性要真成立**：删备份 + 删导出文件 + 清库，三者叠加后数据确实回不来——这是老师认可的"合规操作叠加成攻击"的核心逻辑。

**验收**：表里每一行都能说出"我现在就点给你看"。

## 阶段 2：采集端对齐（用任务 2 的新采集器）

## 阶段 3：服务端与检测侧对齐

- [ ] 3.1 `config/asset_profiles/book_system.yaml` 的 `target_systems` 与实际 `http.host` **精确一致**（含端口、大小写），否则画像不命中 → 敏感度和角色基线全失效
- [ ] 3.2 `resources` 覆盖动作字典里出现的所有 URI（`/admin/*`、`*backup*`、`*export*`、`/reports*` 等）
- [ ] 3.3 `operator_roles` 里的 ID 改成真实的 `op_reader / op_editor / op_admin`（现在写的是 `op_sjg / op_guest`）
- [ ] 3.4 规则 `any_of` 关键词换成系统实际的动作词（原来那套 `delete_backup` 之类要对齐真实 URL/按钮名）
- [ ] 3.5 三台机 + 服务端统一 NTP 校时，`w32tm /stripchart` 确认偏差 < 1s
- [ ] 3.6 先确认跨通道重复写入问题（`docs/M5_M8_工作总结与合谋实验方案.md` 第五节第 1 条）是否影响本实验；若有，实验期间至少加 `(host, operator, ts, collector, uri)` 幂等去重，否则一次操作算两次，评分和证据链都不干净

**验收**：`GET /asset-profiles` 能看到画像；`/collusion/rules` 里规则是改过的版本；时钟对齐。

## 阶段 4：正常行为基线（对照组，必须有）

- [ ] 4.1 三人各做一组正常业务，持续 15–20 分钟：查书、借书、还书、改库存、看报表
- [ ] 4.2 记录：事件条数、风险等级分布
- [ ] 4.3 **要求：不出现 HIGH**（允许 LOW 线索）
- [ ] 4.4 若基线就出 HIGH → 先回去调规则/画像/阈值，**不许带着假阳性进攻击阶段**

**验收**：基线期 HIGH = 0，且三人事件都能按 operator 分开检索。

## 阶段 5：逐个剧本执行（一次只演一个）

- [ ] 5.1 每个剧本开始前记录时间戳；跑完等窗口 flush（默认 15 分钟短窗 + 10 秒宽限），再跑下一个
- [ ] 5.2 严格按动作字典的顺序操作（顺序规则是"有序子序列"，乱序就命不中）
- [ ] 5.3 每个剧本填一张记录表：谁、几点、点了什么、期望命中哪条规则、实际命中什么、评分构成
- [ ] 5.4 **至少保留 1 个"没命中"的剧本**，如实写进报告并分析原因（比全绿更可信）
- [ ] 5.5 全程录屏 + 关键页面截图（老师要的"切身感受"就在这里）

**验收**：至少 3 个剧本按预期命中，且每个命中都能在系统后台找到对应的真实操作记录。

## 阶段 6：证据链与指标核验

- [ ] 6.1 `GET /collusion/events?level=HIGH` 逐条核对：涉及操作员对不对、时间窗对不对、事件序列是否完整
- [ ] 6.2 `GET /collusion/incident-report?days=1` 导出 Markdown 报告
- [ ] 6.3 计算四个指标：

| 指标 | 公式 | 期望 |
|------|------|------|
| 命中率 | 命中剧本数 / 注入剧本数 | ≥ 75% |
| 误报率 | 对照组 HIGH 数 / 正常操作总数 | 越低越好，写真实值 |
| 证据完整率 | 含完整时间线的事件数 / 风险事件数 | 接近 100% |
| 检测时延 | 最后一步操作时间 → 风险事件落库时间 | 记录实际值 |

- [ ] 6.4 与模拟器 `cert_r42` 的结果对比：真实实验和模拟差在哪（这条是加分项，说明你懂"模拟 ≠ 真实"）
