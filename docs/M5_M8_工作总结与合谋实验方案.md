# AuditForwarder M5–M8 工作总结与合谋实验方案

> 更新日期：2026-10-22

---

## 一、一句话说明这个系统

AuditForwarder 是一套**多操作员行为审计 + 合谋检测**系统：

- 每个操作员的主机装一个采集端，记录他在受管系统上做了什么；
- 服务端集中保存这些记录，并判断「几个人配合起来」有没有干坏事；
- 判断结果不是一句「有风险」，而是给出**可复核的证据链**：谁、在什么时间、对什么对象、做了什么、触发了哪条规则、图谱上是什么关系。

和普通日志系统的区别：

| 普通日志系统 | 本系统 |
|--------------|--------|
| 按主机存日志 | 按**操作员身份**贯通（同一人换机器也能串起来） |
| 单条日志查关键字 | 跨事件、跨操作员、带时间窗的**有序行为序列**检测 |
| 报警靠阈值 | 规则 + 资产画像 + 图关系 + 规则证据链 |
| 告警后靠人猜 | 每条风险事件可导出完整证据时间线 |

## 二、M5–M8 做了什么（通俗版）

### M5：让「谁做的」这件事贯通到底

**问题**：原来只知道「某台主机发生了删除」，不知道是哪个操作员做的。

**做的事**：

1. 客户端配置新增 `operator`（操作员 ID / 显示名），GUI 也有输入框；
2. 心跳、事件批次、操作日志三路上报都带上操作员身份；
3. 服务端建立**操作员台账**（`data/operators.json`）：谁绑定了哪台主机、在线状态、最近上报；
4. 采集 HTTP 行为：客户端内置本机 HTTP 代理，把对图书系统这类 Web 系统的访问记成结构化事件（方法 / 主机 / URI / 状态码 / 请求体长度，请求体自动脱敏）；
5. Web 控制台新增「操作员台账」页面，可筛选、可登记、可发现换机绑定异常。

**结果**：一条操作日志从采集到入库，全程带着 `operator_id`，可以按人检索。

### M6：统一事件模型 + 危害规则

**M6-1 统一事件模型（对齐 OCSF 子集）**

不同采集器字段五花八门，规则没法统一写。所以增加一层映射，把每条事件统一成 7 个字段（只写进 attrs，不改原有结构、不影响哈希链）：

`actor`（谁）/ `activity_name`（动作）/ `object`（对象）/ `outcome`（结果）/ `severity_id`（严重度）/ `target_system`（受管系统）/ `metadata`（元数据）

**M6-2 资产画像 YAML**

把「图书系统」这类受管系统写成一个配置文件：有哪些资源、敏感度多少、什么角色能做什么操作。这样方案是通用的，换一个系统只换 YAML。

示例：`config/asset_profiles/book_system.yaml`（reader / editor / admin 三个角色基线）。

**M6-3 Sigma 风格关联规则**

支持真正意义上的「多步行为」规则：

- `group_by`：按操作员分组、按对象分组，或按资产组分组；
- `timespan`：微秒级时间窗；
- `ordered sequence`：动作必须按顺序发生（中间可以夹杂无关操作）。

命中即直接定级（HIGH / MID / LOW），并写风险事件 + 平台告警；同规则同分组有降噪窗口，避免刷屏。

内置示例：

| 规则 | 含义 | 分组方式 |
|------|------|----------|
| R-001 | 备份销毁合谋（删备份 → 卸载卷 → 快照） | 资产组 |
| R-004 | 数据批量外泄（提权 → 导出 → 清除） | 资产组 |
| R-006 | 同一操作员导出后清除 | 操作员 |
| R-007 | 同一对象上提权后外泄 | 对象 |

### M7：合谋图谱（从「主机图」升级为「操作员图」）

- 节点 = 操作员；
- **同对象共现边**：两人在时间窗内操作了同一个对象；
- **角色互补边**：两人的动作构成危险组合（一人删备份 + 一人卸载磁盘）；
- **时间窗稠密度**：窗口内「实际出现的操作员对 / 理论上可能的两两组合」的最大值，用来衡量小圈子密谋的紧凑程度；
- 图异常只作为**线索因子**（默认上限 25 分），不能单独把风险推到 HIGH。

### M8：模拟器 + 危害定级报告

1. **模拟器** `build/auditforwarder-sim.exe`
   - 场景 `cert_r42`：多名正常操作员 + 4 组合谋攻击剧本；
   - 输出标准 JSONL，直接投给服务端；
   - 可指定种子复现、可关闭攻击做对照组。

2. **危害定级报告** `GET /collusion/incident-report?days=7`
   - 输出 Markdown：概览统计、规则汇总表、逐事件证据链（涉及操作员、对象、时间窗、评分构成、图谱指标、时间线表格）。

3. **演示脚本** `scripts/demo_m8.ps1`
   - 登录 → 生成事件 → 单批次投递 → 导出报告，一条命令跑完。

**本机实测**：42 条事件单批次投递，得到 HIGH=6 / MID=2 / LOW=3，R-001 / R-004 / R-006 / R-007 全部命中，报告证据链完整；全量单元测试 **638 项通过**。

## 五、已知问题（正好是后续优化的抓手）

1. **跨通道重复**：同一次 HTTP 操作可能同时经「批次 ingest」和「operation-logs」写入 events 表，产生两条记录。
   → 存储优化时按 `(host, operator, ts, collector, http.uri)` 做幂等去重。
2. **日志检索噪音**：只用 `operator_id` 当关键词会被文件采集噪音占满。
   → `/db/query` 增加 `collector` / `category` 过滤参数。
3. **文件存储膨胀**：操作日志、风险事件、告警都是按追加写的 JSONL，文件会越写越大。
   → 按「天 + 主机 + 采集器」分片，保留期分级（低风险 90 天、中高风险 180 天已在风险事件生效）。
4. **长窗口与短窗口重复计分**：同一攻击会同时命中短窗口与长窗口（长窗口等级会自动降一级），演示时看起来像「重复告警」。
   → 报告里做「同源事件合并」，或界面标注「长窗口弱线索」。
5. **多机联调未验证**：目前只做过本机冒烟。

## 六、后续合谋实验方案（建议版）

### 6.1 实验目标

在真实图书管理系统上，验证系统能否：

1. 正确采集多名操作员对同一套系统的操作，并保持身份不串；
2. 在**不误报正常业务**的前提下，命中预设的合谋攻击剧本；
3. 给出可复核的证据链与危害定级报告。

### 6.2 环境拓扑

```
[操作员 A 主机] ─┐
[操作员 B 主机] ─┼─ 采集端 agent（HTTP 代理 / 文件 / 进程）─→ [服务端 8443] ─→ 风险事件 + 报告
[操作员 C 主机] ─┘                                             ↑
                                                     [图书管理系统 book-web]
```

- 1 台服务端（管理端 + 检测引擎 + 存储）
- 2–3 台客户端（每人一台，或同机多账户模拟）
- 1 个图书管理系统（部署在服务端或独立主机）
- 网络：Radmin VPN / 局域网均可

### 6.3 分阶段步骤

**阶段 0：环境与账号**

- 部署图书系统，准备 3 个角色账号：普通读者、图书管理员、系统管理员；
- 服务端启动，客户端配置 `operator.id` / `operator.name`，每人一个唯一 ID；
- 在客户端配置 `collectors.http_proxy.target_hosts` 指向图书系统主机。

**阶段 1：正常行为基线采集**

- 每人完成一组正常业务：查书、借书、还书、改库存、看报表；
- 观察 `GET /operators` 是否自动登记、`/db/query` 是否带 `operator` 列；
- 确认正常行为**不产生 HIGH 风险事件**（允许 LOW 线索）。

**阶段 2：资产画像与规则配置**

- 为图书系统写画像：`config/asset_profiles/book_system.yaml`（已有示例，按实际系统微调）
  - 现有示例资源：`/books*`（data_record，internal）、`/admin/*`（config，confidential）、`*backup*`（backup，secret）、`*credential*`（credential，secret）
  - 建议补充：`/reports*`(confidential)、`/readers*`(confidential)
  - 现有示例角色：reader 只读、editor 读/建/改、admin 全量（`denied_actions` 优先，如禁止 `delete_backup`）
  - `target_systems` 必须与采集到的 `http.host`（可带端口）一致，否则画像不会被命中
- 规则：保留 R-001/R-004/R-006/R-007，按图书系统实际动作词调整 `any_of` 关键词；
- 通过 `PUT /collusion/rules` 或直接改 `policies/collusion_rules.json` 热加载，无需重启。

**阶段 3：攻击剧本执行**

按「一次只演一个剧本」的原则，每个剧本之间留出空窗：

| 剧本 | 参与人 | 动作序列 | 期望 |
|------|--------|----------|------|
| A 备份销毁 | DBA1 / DBA2 / DBA3 | 删备份 → 卸载备份卷 → 打快照 | R-001 命中 + 图谱互补边 |
| B 批量外泄 | 管理员 / 运维 | 提权 → 导出数据库 → 清表 | R-004 命中 |
| C 个人窃取 | 单一内鬼 | 导出报表 → 清除报表 | R-006 命中（operator 分组） |
| D 对象级合谋 | 内鬼甲 / 内鬼乙 | 甲提权 → 乙导出同一对象 | R-007 命中（object 分组） |
| 对照组 | 正常操作员 | 与攻击同时间窗的正常业务 | 不产生 HIGH |

**阶段 4：结果核验**

- `GET /collusion/overview`：风险事件分布是否符合预期；
- `GET /collusion/events?level=HIGH`：检查涉及操作员、时间窗、证据时间线；
- `GET /collusion/incident-report?days=1`：导出报告，逐条核对证据；
- 统计指标：
  - 命中率 = 命中剧本数 / 注入剧本数
  - 误报率 = 对照组产生的 HIGH 事件数 / 正常操作总数
  - 证据完整率 = 含完整时间线的事件数 / 风险事件数
  - 平均检测时延 = 最后一步操作时间 → 风险事件落库时间

**阶段 5：报告与演示**

- 用 `/collusion/incident-report` 生成 Markdown 报告；
- 附上 `data/collusion/collusion_events.jsonl` 与告警文件作为原始证据；
- 演示路径：登录控制台 → 操作员台账 → 风险事件 → 证据链 → 导出报告。

### 6.4 服务端界面与存储优化的建议顺序

1. **先定实验必需页面**（约 5 个），其余页面隐藏或加开关，不急着删代码；
2. **日志分类**：列表页增加 `collector` / `category` / `target_system` / `risk_level` 四个筛选器与列；
3. **存储分片**：`data/operation_logs/<host>/<YYYYMMDD>/<collector>.jsonl`，查询按日期范围定位文件；
4. **去重**：入库前对 `(host, operator, ts, collector, uri)` 做幂等判断；
5. **保留策略**：按等级/日期清理，并在界面显示「当前占用 / 最早记录时间」。

### 6.5 风险与注意事项

- **时钟偏差**：多机时间不同步会让微秒时间窗失效，实验前统一 NTP；
- **批量投递**：如果手工灌数据，必须**一次性批量**投递（逐条会让时间窗提前冲刷，多步规则命不中）；
- **采集范围**：HTTP 代理只覆盖浏览器/命令行走代理的流量，直接连库的客户端需要数据库审计适配器或手工导入；
- **误报**：攻击剧本与正常业务尽量错开时间与对象，便于归因；
- **隐私**：`capture_body` 默认关闭，开启时请求体已脱敏，演示前确认无真实敏感数据。
